North Star do tare.tools.backlog-graph: Motor Determinístico de DAG de Tarefas e Framework de Execução Topológica para Humanos e Agentes de IA

Este estudo formaliza a especificação arquitetural definitiva e os fundamentos matemáticos do **`tare.tools.backlog-graph`**, um motor determinístico de gestão de backlogs em Grafo Acíclico Dirigido (DAG) e framework de execução topológica projetado para desenvolvedores humanos e agentes autônomos de IA. Superando o modelo linear e cego dos issue trackers tradicionais (Jira, Linear, GitHub Projects), o `tare.tools.backlog-graph` resolve as três patologias clássicas de entrega de software: *Blocker Blindness*, *Blind Prioritization* e *Frontier Hallucination*. O sistema é implementado em **Python puro com zero dependências externas (stdlib pura)**, garantindo portabilidade universal e execução instantânea. O documento formaliza a função de ordenação total estável da fronteira de execução ($\text{Priority} \rightarrow -\text{Depth} \rightarrow \text{Lexicographical ID}$), define o algoritmo de canonicalização de estado baseado em JSON Canonicalization Scheme (RFC 8785 / JCS), estabelece o protocolo de mutação transacional Compare-And-Swap (CAS) sob lockfile de exclusão mútua, e detalha o compilador de *Implementation Packets* com *Definition of Done* (DoD) para swarms multiagente. A solidez do framework é demonstrada por uma suíte de 79 testes unitários e de integração cobrindo 100% dos fluxos de validação acíclica, reconciliação de projeções e mutações.

1. Scope & Problem Formulation

O desenvolvimento de software moderno não é uma sequência linear de tickets nem um quadro Kanban de colunas irrestritas: é uma rede de dependências contratuais, pré-requisitos lógicos e superfícies de integração.

$$\text{Tarefas no Backlog} \xrightarrow{\text{Topologia DAG}} \text{Cálculo de Fronteira (Ready)} \xrightarrow{\text{Implementation Packet}} \text{Execução Autônoma por IA} \xrightarrow{\text{CAS Landing}}$$

1.1. As Três Patologias dos Trackers Tradicionais

  1. Cegueira de Bloqueios (Blocker Blindness): Trackers convencionais tratam tarefas como cartões isolados. Quando uma entrega crítica trava, engenheiros perdem horas rastreando comentários em tickets para descobrir qual dependência esquecida causou o bloqueio.
  2. Priorização Ilusória (Blind Prioritization): Marcar um ticket como P0 é inútil se os seus pré-requisitos P2 não forem implementados primeiro. A prioridade real é uma propriedade da cadeia topológica inteira.
  3. Alucinação de Fronteira (Frontier Hallucination): Agentes de IA autônomos (Claude, Codex, Devin) recebem listas desordenadas e tentam implementar código para o qual as interfaces base ainda não existem, gerando patches incompatíveis e retrabalho.

1.2. A Solução do Backlog Graph

O tare.tools.backlog-graph substitui a adivinhação manual por computação determinística:

  • Apenas tarefas cujos pré-requisitos estão provadamente DONE entram no estado READY;
  • O motor calcula a qualquer momento a fronteira exata de trabalho viável (backlog next);
  • O comando backlog why <ID> decompõe instantaneamente a árvore de causas de qualquer bloqueio.

3. Especificação Matemática e Algoritmo de Ordenação Total (Findings)

3.1. Ordenação Total Estável da Fronteira

Para garantir que múltiplos agentes de IA distribuídos cheguem exatamente à mesma decisão de próximo passo ótimo, o motor aplica a tupla de ordenação total estrita:

$$\text{FrontierRank}(v) = \Big( \text{PriorityWeight}(v),\ -\text{CriticalPathDepth}(v),\ \text{LexicographicalID}(v) \Big)$$

Onde:

  • $\text{PriorityWeight} \in { \text{P0} \mapsto 0,\ \text{P1} \mapsto 1,\ \text{P2} \mapsto 2,\ \text{P3} \mapsto 3 }$;
  • $\text{CriticalPathDepth}(v)$ é o comprimento do caminho mais longo de dependentes a jusante destravados pela conclusão do nó $v$;
  • $\text{LexicographicalID}(v)$ garante desempate estável ($O(1)$) entre nós de mesmo peso e profundidade.

3.2. Estado READY como Função Derivada Pura

Diferente de status mutáveis pelo usuário, o estado READY é matematicamente derivado:

$$\text{IsReady}(v) \iff (\text{Status}(v) == \text{TODO}) \ \land \ \forall u \in \text{Prerequisites}(v),\ \text{Status}(u) == \text{DONE}$$

4. Transações CAS sob Exclusão Mútua & Hash Canônico RFC 8785 (Governance)

4.1. Hash de Revisão Content-Addressed (RFC 8785 / JCS)

O identificador de revisão do grafo garante que qualquer modificação seja tamper-evident:

$$\text{revision_hash} = \text{sha256}\Big(\text{JCS_CanonicalJSON}\big(\text{Graph} \setminus {\text{"revision"}}\big)\Big)$$

4.2. Protocolo Transacional de 5 Etapas:

        Client->>Disk: 4. ATOMIC REPLACE: Grava .tmp, fsync e os.replace
        Client->>Lock: 5. RELEASE LOCK
    end

4. Limitations & Threats to Validity

O comando backlog packet --task <ID> gera um pacote estruturado em Markdown (PACKET.md) contendo:

  1. Identidade e Metadados: ID da tarefa, título, prioridade e especificação causal vinculada (spec_ref: SPEC-042);
  2. Contexto de Pré-requisitos: Resumo dos contratos e interfaces produzidos pelas tarefas a montante já concluídas;
  3. Definition of Done (DoD): Lista executável de critérios de aceite que os oráculos de teste devem falsificar e verificar;
  4. Âncoras de Código: Símbolos e arquivos alvo governados por SpecGraph.
